はい、原因はかなり絞れます。しかも、この症状はリポジトリ内の実走結果でほぼ同じ形で再現済みです。

結論

起きていることは、だいたい次の連鎖です。

開始直後の特別な横抜け判定 start-grid breakout に入れない、または一度入っても解除される
→ 通常の追い越し条件へ戻る
→ その時点では前車へ近づきすぎて通常追い越しを開始できない
→ Followへ遷移
→ Follow中は横方向のgap plannerが無効なので、そのまま前車についていく

したがって、単純に「内側が認識できていない」というより、スタート時に一度しかない横抜けの機会を逃すと、Followへ吸い込まれる構造になっています。

リポジトリ内で実際に確認されていた原因
1. 前車は見えたが、横の車両判定が1周期遅れていた

実走 20260721-221420 では、D1が停止中の前車を先に検出したものの、別車両がまだ side vehicle として分類されていませんでした。以前の実装は前車判定と横車両判定の同時成立を要求していたため、breakout対象にならず、中心間2.65 mで直接 SafetyBrake に入りました。

現在のコードではこの点は修正され、breakout入口に必要なのは has_front_vehicle であり、has_side_vehicle は必須ではなくなっています。

この修正後も同じ挙動なら、まず実行中のコンテナが古いバイナリを使っている可能性があります。

2. 初期配置の横ずれから通過方向を固定し、空いている側を評価していなかった

実走 20260721-222751 では、D1が初期配置の横ずれだけを根拠に左側を選び、実際には空いていた右側を opposite staggered side として評価しませんでした。つまり、見た目では空いている側があっても、最初の横位置から反対側を候補外にしていました。

現在は左右両方の、車体膨張後の実際のコリドー幅を評価し、広い方を選ぶよう変更されています。

ただし重要なのは、**現在のスタート専用ロジックは「イン側優先」ではなく「実際に広い側優先」**だという点です。左右両方が成立した場合、コリドー幅が大きい方を選び、同幅のときだけ通常の幾何的な優先側を使います。

したがって、内側が空いて見えても、

壁までの距離
前車を膨張させた占有範囲
他のスタート車両
予測余白

を含めて外側の方が数値的に広ければ、内側は選びません。

3. Overtakeへ入っても、前方危険判定が横移動を解除していた

同じ 20260721-222751 では、V2X behavior側では

desired=Overtake
grid_breakout=1
gap=1

となっているのに、OvertakeLine側が、

ShiftOut -> Idle, reason=safety brake

を繰り返していました。つまり、上位判断では横抜け可能なのに、横軌道生成側が前方危険判定をもう一度適用し、横移動を消していました。

現在は、有効なstart-grid breakoutでgapと実行zoneが成立している間は、close-front riskだけでOvertakeLineを消さないよう修正されています。

4. 横抜けに入っても、前車速度＋0.5 m/sに抑えられていた

これは「気づいたら前車に追従している」という現象に最も近い原因です。

実走 20260721-224214 では、D1とD2はいずれも開始後約0.05秒で空いているコリドーを選択し、start-grid breakout へ入っていました。しかしbehavior側が37 km/hのスタート速度を許可しているのに、OvertakeLine側が別の速度capを重ねていました。

その結果、D2の有効速度参照は 3.42 m/s、つまり前車速度＋0.5 m/sに抑えられました。十分な速度差が作れないまま前車についていき、やがて横gapが消失し、最終的に Follow -> SafetyBrake へ戻っています。

現在のコードには、この二重capを解除する修正が入っています。validated breakout中は front_cap_release_ready=true とし、breakout behaviorだけに速度参照を持たせています。コードコメントにも、旧処理が「前車について最初のヘアピンへ入る」原因だったと明記されています。

なぜ一度Followになると内側へ行かなくなるのか

現在の設定では、

v2x_follow_gap_planner_enabled: false

です。つまり、状態が Follow になった後は、空いている横gapを使って抜ける経路を作りません。基本軌道を追いながら速度だけ前車に合わせます。follow_preposition は有効ですが、これは0.9 mの弱い横参照であり、本格的な追い越し軌道ではありません。

さらに通常追い越しの新規入口には、

v2x_overtake_guard_min_front_distance: 5.0

が必要です。スタート直後のbreakoutを逃した時点で前車との距離が2～3 m程度になっていると、通常の追い越し入口条件をもう満たせません。

コード上も、前車が存在する状態でgapまたは実行zoneが不成立なら、そのまま Follow を選び、Follow速度制限を適用します。

これが、

最初は内側が空いていた
少し経つと前車との距離が縮まった
その後ずっと前車追従

となる直接的な理由です。

現在の最新版でも残っている入口上の弱点

現在のbreakout入口には、まだかなり厳しい条件があります。

front_speed <= stationary_speed_threshold

つまり、前車速度が停止車閾値以下でなければ新規breakoutを開始しません。

現在の閾値は、

v2x_low_speed_avoidance_max_front_speed: 0.2

なので、前車が初回の有効判定時にすでに0.2 m/sを超えていると、スタート専用breakout対象になりません。

また、V2X behaviorはレースセッションがactiveになるまでは即座にCruiseを返すため、Ready中にbreakout対象IDを確実にラッチしておく構成にはなっていません。

したがって最新版でも、

Start直後の最初の有効V2X判定が少し遅れる
その間に前車が0.2 m/sを超える
stationary breakoutとしてラッチされない
すでに前車との距離は5 m未満
通常追い越しにも入れずFollow

という競合は残り得ます。

「内側が空いている」のコード上の意味

現在の設定では他車を自車中心から半径1.45 mの禁止領域として扱い、さらに予測余白0.1 mを追加します。壁側は0.8 m縮めています。

したがって、画面上で2～3 mほど空いて見えても、planner上は、

内側幅
－ 1.45 m
－ 0.1 m
－ 0.8 m

となり、実行可能な残り幅がほとんどないことがあります。

現在のstart-grid breakoutは、この膨張後コリドー幅を左右で比較し、広い側を選びます。「コーナーのインだから選ぶ」という戦略にはなっていません。

まずログで判定できます

最新版で期待される開始直後のログは、

None -> Overtake
reason=start-grid breakout
grace=1
grid_breakout=1
OvertakeLine: Idle -> ShiftOut
cap_release=1

です。リポジトリ自身もこれを実走acceptance条件にしています。

一方、次のログなら原因が判別できます。

start-grid breakout opposite staggered side

なら、左右両方を評価する修正前のバイナリです。

desired=Overtake, grid_breakout=1
OvertakeLine: ShiftOut -> Idle, reason=safety brake

なら、前方危険判定によるline解除修正前です。

cap_release=0
v_ref ≒ front_speed + 0.5

なら、二重速度cap修正前です。

Start grid grace expired...

の直後にtargetやsideが消えるなら、5秒経過時の継続修正前です。

start-grid breakout unavailable

なら、実行中コードは最新版に近く、膨張後の左右gapのどちらか、または両方が不成立です。この場合は同じログに出る左右の理由と corridor_width を確認すべきです。

ただし、ビルドと580件のテストは通っている一方、最新版修正後の make dev3 実走確認はまだ未完了です。

古い実行バイナリなら、既知の不具合そのもの
最新HEADなら、修正は入っているが実走未確認
最新HEADでも再現するなら、最有力は「前車が0.2 m/sを超えてから初回判定された」か「膨張後の内側gapが不成立」

です。

修正方針

最も堅い修正は、現在速度だけでなく、Start前またはStart瞬間に静止していた事実を一定時間保持することです。

例えば、

v2x_start_grid_static_latch_hold_sec: 1.0

を追加し、

現在0.2 m/s以下
または
Start前1秒以内に同じIDを静止車として観測済み

ならbreakout候補を維持します。これならV2X更新周期と発車タイミングの競合で入口を失いません。

さらに本当にイン側を優先したい場合は、現在の「最大幅優先」とは別に、

v2x_start_grid_prefer_inner: true
v2x_start_grid_inner_width_tolerance: 0.2

のような方針を追加し、イン側が実行可能で、最大幅との差が0.2 m以内ならインを選ぶのがよいです。

5 mの通常追い越し入口を縮めるより、スタート専用breakoutのラッチを確実にする方が、追突を増やさず狙った内側へ出られます。

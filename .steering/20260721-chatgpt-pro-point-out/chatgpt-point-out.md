総評

結論から言うと、この develop_july はかなり本気で勝ちに行く実験車になっています。MPC、V2X追い越し、停止車回避、接触後の後退復帰、スタート加速まで揃っており、低い安全マージンやハードカーブでの追い越しも含め、方向性は今回の「多少ぶつけても6周で1着」という目的に合っています。

一方、現状はまだ**「個別シナリオを攻めて通せるソフト」から「6周レースを高確率で勝ち切るソフト」への最後の一段が不足**しています。特に重要なのは、さらに安全マージンを削ることではなく、次の3点です。

優先度	指摘	6周レースへの影響
P0	停止車回避中に3 m/sへ張り付き続ける制御経路	1回あたり数秒、毎周なら十数秒を失う可能性
P0	復帰中の一時異常がセッション終了まで停止へつながる	接触許容レースなのに事実上DNF
P1	OSQPを毎周期作り直し、1回の失敗から即減速	混雑時・追い越し時にランダムなタイムロス
P1	最新の4 m ShiftOut・ハードカーブ攻撃設定が6周未検証	単体テストは通るが勝率不明
P1	現在位置を毎周期「全経路中の最近傍点」へ再接続	接触でコースを外れた際に別区間へ飛ぶリスク
P2	周回数や順位差に応じたレース戦略がない	先頭でも同じリスクを取り、最終周でも攻撃度が同じ

なお、safety_margin_scale: 0、壁余白0.1 m、狭いgap、速度差、ハードカーブ進入などは、今回の目的から見て欠陥扱いしていません。むしろ攻め方として妥当です。

1. 最優先：停止車回避が実質3 m/s固定になっています

ここが最も明確なラップタイム損失です。

設計上は、

停止車の横へ移動中は shift_velocity
通過回廊へ入った後は pass_velocity

へ戻す意図になっています。ヘッダにも「回廊へ入ったら設定された通過速度へ戻す」と明記され、Plannerも回廊進入後に速度を切り替えています。

設定値は、

通過速度：11.1 m/s
横移動速度：3.0 m/s

です。

ところが実際の制御所有権を見ると、直接操舵コントローラは停止車列全体を抜け、再合流するまでラッチされます。

そして low_speed_shift_velocity_mps_ が設定されるのは、まだ回廊へ入っていないときだけで、その値は shift_velocity の3 m/sです。
直接操舵中は、そのキャッシュされた速度をそのまま毎周期返しています。

つまりコード経路としては、

横移動開始 → 3 m/s
回廊進入 → Plannerは11.1 m/sを計算する
しかし直接操舵が所有権を持ったまま → 実指令は3 m/sのまま
車列通過・2秒clear hold・再合流まで3 m/s

となる可能性が高いです。

8 mだけ3 m/sで通る場合でも、11.1 m/sと比べ約 1.95秒失います。12 mなら約 2.92秒です。仮に毎周1回あれば、6周で約12～18秒。追い越し閾値を数十cm攻めるより圧倒的に大きい差です。

推奨修正

直接操舵を次の3フェーズに分けるべきです。

Shift：3～4 m/sで横移動
Pass：回廊進入後、MPCへ早期ハンドオフ。失敗時だけ直接操舵を6～8 m/sで継続
Rejoin：4～6 m/sで復帰し、MPC probe成功後に完全移譲

最も良いのは、pass_corridor_enforced == true になった時点でMPCのprobe solveを行い、成功すればすぐMPCへ渡す方法です。現在は「車列が完全に消えて再合流するまで」ハンドオフを待つため、待ちすぎです。

単純に同じ横フィードバックのまま11.1 m/sへ上げると操舵ゲインが合わなくなる可能性があるため、まず6 m/s程度まで段階的に上げるA/Bが無難です。

2. 接触許容レースなのに、復帰処理がDNF方向へ寄りすぎています

接触後の復帰機能自体は非常に丁寧です。ただし、今回のレース方針にはfail-closedが強すぎます。

現在はV2X完全性に固定車両数を使用しており、3台走行では他車2台、4台なら設定を3へ手動変更する前提です。単独・欠落状態ではfail-closedになります。

さらに復帰中に制御failsafeが発生すると recovery_fault_latched_ が立ちます。
この状態になると、以後はセッションリセットまで停止指令を出し続けます。

これは実車なら理解できますが、今回の目的では、

一時的なV2X欠落
0.5秒のodom timeout
復帰中の一度のsolver失敗
車両数設定と実参加台数の不一致

のいずれかで、残り5周を捨てる可能性があります。

推奨修正

シミュレーター用の race_relaxed_recovery を別モードとして入れるべきです。

スタート時に一定時間観測された車両IDから参加台数を自動確定
以後は「全台同時に新鮮」を要求せず、車両ごとの最終観測時刻で評価
V2X不足時は無制限に動かすのではなく、0.2～0.4 mの短い接触改善ステップだけ許可
各ステップ後に停止・再評価
odom、gear、command finite、現在footprint、短い進行方向回廊が0.5秒正常ならfault latchを自動解除
永久ラッチはギア不明、非有限指令、復帰方向が完全に不明な場合だけ

「安全機能を外す」のではなく、停止し続けるより、短距離ずつ試して前進復帰する設計に変えるのがレース向きです。

3. OSQPの使い方が、40 Hzレース制御として重いです

制御周期は40 Hz、つまり1周期25 msです。

ところが現在は毎回、

Eigen行列を圧縮
CSC配列を新規確保・コピー
osqp_setup
osqp_solve
workspace cleanup

を行っています。

ノードはSingleThreadedExecutorなので、solver実行中はodomやV2X callbackも同じスレッド上で待ちます。

しかも1回solverが失敗すると、その周期から直ちに減速fallbackへ入ります。
実走分析でも、比較runでOSQP failureが31件、34件と記録されています。

この構成では、混雑や追い越しで制約が急変した瞬間に、

solverが重くなる
callbackが遅れる
次の問題も変化が大きくなる
maximum iterations
即減速
追い越し失敗

という悪循環が起きやすいです。

推奨修正

優先順は次の通りです。

Persistent OSQP workspace

構造が同じ間は osqp_setup を毎回行わず、q/l/u と行列値だけ更新します。前周期解を1ステップずらしてwarm startしてください。

solver時間の計測

setup_us、solve_us、total_us、iterationsをログへ出し、p50、p95、p99を集計します。平均ではなくp99が25 msを超えていないかを見るべきです。

レース向けfallback

1～2周期の失敗：直前の有効解をシフトして使用、加速だけ禁止
3～4周期連続：緩やかに減速
非有限値、無効bounds、stale odom：即停止

現在のように「maximum iterations 1回」と「NaN」を同じ重さで扱う必要はありません。

callback分離

solver用workerへ問題のsnapshotを渡し、odom/V2X callbackを止めない構造が理想です。ただし、共有状態を無造作にMultiThread化するより、最新snapshotをロック付きで渡す方式が安全です。

5. 接触後に別の経路区間へ飛ぶ可能性があります

現在位置更新では、毎周期、経路上の全waypointからユークリッド距離だけで最近傍点を探しています。
そして、その結果で wp_id と進捗 s を毎回上書きしています。

衝突で横向きになったり、ヘアピンの反対側や並行区間へ近づいた場合、コース進行方向を無視して別区間へスナップする可能性があります。そうなると、

前車・後車判定
追い越し禁止区間
カーブ内外判定
lateral error
stuck判定の進捗
Return完了判定

がまとめて壊れます。

これは車載品質の問題ではなく、ガンガン接触するレースだからこそ重要です。

推奨修正

通常時は前回WPを中心に、例えば -10 ～ +40 点だけを検索します。

候補には、

距離
経路接線と車両yawの差
前回からの進捗変化
現在速度から到達可能な距離

を使ってスコアを付けます。

全経路検索へ戻すのは、

明示的なセッションリセット
ローカル候補まで2～3 m以上離れた
一定時間進捗が取れない

場合だけで十分です。周回境界をまたぐunwrapped progressも別に保持すべきです。

6. 「速く走る制御」はありますが「6周を勝つ戦略」がありません

周回数とラップタイムは受信していますが、現状はログ出力とカウンタ更新だけです。

そのため、

先頭を走っていてもハードカーブでリスクの高い並走を続ける
5周目まで後方でも1周目と同じ攻撃度
大差で前にいるのに接触回避より追い越し準備を優先する
最終周でも通常のcooldownやholdを維持する

という状態になります。

6周で1着を狙うなら、最低限次の3モードを入れた方が勝率が上がります。

LEAD

自車の lap * track_length + s が全車最大で、後続に十分な差がある状態。

ハードカーブでの新規追い越し進入を抑制
既に横にいる車だけ抜き切る
permanent-stopにつながる接触だけ避ける
素の最速ラインを優先

前に遅い車がいる通常状態。

内差し／外回り
closing 2.0 m/s

を使う主戦モードです。

最終周で先頭でない状態。

curve cooldown短縮
Return前でも次の前車を先読み

solverの1周期fallbackでは減速しない

現在あるV2Xコース進捗を使えば、順位topicがなくても概算順位は作れます。

良いところ

このブランチで残すべき部分も明確です。

追い越しについては、以前の「横移動未完了なのにPass速度を解放する」問題に対し、横位置収束をPass条件へ加え、前走車cap解除条件を分離した修正は非常に良いです。

また、攻めたハードカーブ進入を許可しつつも、

EmergencyBrake
solver failure

NaN/Inf

は残しており、「何でも無条件に突っ込む」実装にはなっていません。

moving-frontへの距離連動速度capも、過去ログでは連続近接状態を大きく減らしています。

pure coreへ判定ロジックを切り出し、追い越し条件を多数の単体テストで固めている点も良いです。ただしパッケージ全体では、現在のtrajectory形式と食い違う既存テストが1件失敗したままです。赤いテストを常態化させると新規回帰を見落とすので、これは早めに直した方がよいです。

壁や接触あったときのフェールセーフが足りない感じ？

うん、「フェールセーフが足りない」より、種類のバランスが逆という感じです。

壁・接触時の検知や停止処理そのものはかなり多いです。むしろ、

odom異常で停止
solver失敗で減速
復帰中のV2X不完全で停止
ギア状態不明で停止
復帰中の異常をセッション終了までラッチ

と、止める側は強いです。

足りないのは、レース向けの次のフェールセーフです。

1. 接触したまま押し続けるのを早く検知する仕組み

現在はcollision hintや進捗低下を使っていますが、壁へ斜めに刺さってタイヤだけ回っている状態を、もっと直接判定した方がよいです。

例えば0.3～0.5秒間、

速度指令は前進
実速度がほぼゼロ
経路進捗も増えない
操舵角が大きい、またはcollision状態

なら、即座に通常MPCを諦めて短い後退へ移るべきです。

今のように複数証拠や長めの観測を待つと、その間ずっと壁を押してタイムを失います。

2. 復帰処理が失敗したときの「次の手」が弱い

現状は丁寧に安全確認しますが、一度条件が崩れると停止待ちやfault latchへ行きやすいです。

レース用なら、

0.3～0.5 m後退
停止して再評価
操舵方向を反転して再試行
それでも駄目なら1 m程度の強制退避
前進再合流

という段階的エスカレーションが必要です。

要するに、止めるフェールセーフではなく、脱出するフェールセーフが足りません。

3. 壁接触後の経路復帰が不安定になり得る

接触で車両が横を向いた際、全経路から単純最近傍WPを選ぶため、ヘアピンの別側や並行区間へ飛ぶ可能性があります。

すると復帰操舵が全然違う方向を向き、さらに壁へ押し付けるケースがあり得ます。

ここは、

接触前のWP周辺を優先
進行方向とyawが合う点を優先
大きく後方へ飛ばない
明確にロストしたときだけ全経路再探索

にすべきです。

4. solver失敗時の退避が「減速だけ」

壁際でMPCが解けない場合、現在のfallbackは基本的に減速しつつ操舵を保持または中立へ戻します。

ただ、壁へ向いた状態で操舵を中立化しても、脱出できないことがあります。

壁との接触方向が分かる場合は、

左壁なら右へ切る
右壁なら左へ切る
正面壁なら後退
後方壁なら前進

という接触方向ベースのfallbackを、solverとは別系統で持つべきです。

5. 逆に、永久停止は強すぎる

復帰中の一時的な異常でfault latchが立つと、レース中ずっと停止する可能性があります。

これはフェールセーフ不足ではなく、フェールセーフが強すぎてDNFを作る問題です。

一定時間、

odom正常
ギア正常
指令finite
現在の車体接触が悪化していない
前後どちらかに短い移動余地あり

なら、自動的に再試行した方がレース向きです。

まとめ

壁や接触に対して現在足りないのは、

「異常なら止まる」機能ではなく、
「壁を押し続けず、短時間で脱出し、レースへ戻る」機能です。

特に優先するなら、

前進指令なのに0.4秒進捗ゼロで即stuck判定
接触方向に応じた0.3～0.5 mの退避
失敗時に操舵方向を変えて最大3回再試行
最近傍WPの局所探索化
fault latchの自動解除

この5つです。

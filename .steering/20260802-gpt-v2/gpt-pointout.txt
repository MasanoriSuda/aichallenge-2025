選択したcandidateごとに、

を計算し、deadlineを満たす候補、その中でもbody-clearが早い候補を優先します。

→ V2XBehaviorOutput
→ OvertakeLineState

へ渡され、

実行時も、設定上限の2.0 m/sへ勝手に戻さず、保存したmission値を使います。距離が詰まったときのadaptive closingやunseparated reserveは、そこからさらに低く制限できます。つまり、固定されるのは最低速度ではなく攻撃度の上限です。設計意図はきれいです。

ただし、重要な未解決点がある
P0-1. 同じcandidateを、横と縦で別の速度モデルにより評価している

これが最重要です。

横経路のpreflightでは、必要横加速度を**現在速度current_speed_mps_**で評価しています。

一方、body-clear deadlineでは、

predicted_ego_speed =
    min(v_max, target_speed + selected_closing_speed)

へ瞬時に到達し、その速度で一定走行する前提です。

実際の車両は、

a_max: 1.0
a_min: -1.35
state_prediction_delay_sec: 0.125

で加減速します。

つまり、同じcandidateについて、

横加速度判定: 現在速度
body-clear判定: target速度＋closingへ瞬時変化
実走: 加速度制約と遅延を伴う速度

という3種類のモデルが使われています。

例

仮に、

現在速度: 8.0 m/s
前車速度: 3.33 m/s
選択closing: 2.0 m/s
計画上の自車速度: 5.33 m/s

なら、8.0から5.33 m/sまで1.35 m/s²で減速するのに約1.98秒かかります。

その間、瞬時に5.33 m/sへ下がるモデルより、およそ2.6 m余計に前方距離を消費します。現在の追い越しentry最低距離は3.0 mなので、誤差として非常に大きいです。

逆に現在速度が低ければ、計画速度へ瞬時加速する前提によりbody-clear時刻を楽観視します。

必要な修正

deadlineと横加速度を、同じ時間rolloutで評価すべきです。

for (double t = 0.0; t <= horizon; t += 0.05) {
  ego_v = clamp(
      ego_v + commanded_accel * dt,
      previous_v + a_min * dt,
      previous_v + a_max * dt);

  ego_s += ego_v * dt;
  ego_d = mission_path(ego_s);

  target_s += filtered_target_s_dot * dt;
  target_d += filtered_target_d_dot * dt;

  check_body_overlap();
  check_wall();
  check_lateral_accel();
  check_hard_gap();
}

少なくとも、

現在速度
a_max / a_min
0.125秒の制御遅延
区間速度・曲率速度上限
candidate closing speed

を同じ予測へ入れる必要があります。

P0-2. 左右の最終選択がdeadlineを見ていない

closing speed込みのcandidate選択は各sideの中では適切です。

しかし左・右の最終選択では、現在も主に、

base racing lineを維持できるか
必要横移動量
inner preference
corridor幅
continuous open distance
必要横加速度

で比較しています。body-clear deadline成立可否やdeadline余裕はside選択に渡されていません。

したがって、例えば、

アウト:
  body-clear deadline成立
  横移動0.8 m

イン:
  body-clear deadline不成立
  横移動0.4 m
  inner preference対象

なら、イン側が選ばれる余地があります。

選ばれたインcandidateはdeadline不成立なのでShiftOut ownerを得られず、以前と同じ、

ShiftOut
→ 候補再評価
→ Follow

へ戻る可能性があります。

必要な修正

最もきれいなのは、左右を分けずに、

side × goal × shift distance × closing speed

を一つのcandidate vectorへ入れてグローバル選択することです。

最低限でもside候補へ、

bool body_clear_deadline_feasible;
double body_clear_deadline_slack_sec;
double predicted_body_clear_time_sec;

を追加し、選択優先順位を、

1. deadline成立
2. deadline slackが十分
3. base-line維持
4. body-clearが早い
5. 横移動が小さい
6. 横加速度が小さい

にするべきです。

P1. deadline成立余裕が0.10秒しかなく、最速候補を優先しすぎる

現在のdeadline reserveは、

v2x_overtake_body_clear_deadline_margin_sec: 0.10

です。

candidate comparatorはdeadline成立後、最もbody-clearが早い候補を選びます。したがって、

2.0 m/s candidate:
  deadline余裕 0.11秒

1.4 m/s candidate:
  deadline余裕 0.45秒

でも、2.0 m/s側を選び得ます。

V2X、操舵遅延、追従誤差、曲率制限を考えると0.10秒はかなり薄いです。

body_clear_timeだけでなく、

deadline_slack =
    hard_distance_time - body_clear_time;

を保存し、最低0.25～0.4秒程度をA/Bするのがよいです。これは公式値ではなく、まず試すための候補です。

P1. Recoveryからの再取得で古いmission条件を流用する可能性がある

Recovery -> ShiftOut再取得時は、

fixed_pass_corridor_goal_ey =
    behavior_output.overtake_corridor_center_ey;

へ更新しています。

しかし、この分岐では少なくとも見えているコード上、

mission_shift_distance
mission_closing_speed_limit
mission_body_clear_deadline_feasible
mission_path_frozen

を再計算・再設定していません。

つまり、

旧corridorで選んだclosing/deadline
→ Recovery
→ 新しいcorridor goalへ差し替え
→ 旧deadline成立結果のままShiftOut owner

になるリスクがあります。

修正方針

Recovery再取得は、次のどちらかに限定すべきです。

A. Idleへ戻し、全candidate探索をやり直す

または、

B. side / goal / shift distance / closing speed /
   deadline / total pathを一括で再計算し、
   mission stateをatomicに置換する

goalだけの差し替えは避けるべきです。

P1. deadline_checkedが明示されていない

現在は、

mission_body_clear_deadline_feasible{true}

というbool中心です。

normal front entryでは評価されますが、side-only entryや一部fallback経路などでdeadlineを実際に評価していない場合も、デフォルトのtrueと区別できません。

次の2値を分離すべきです。

bool mission_body_clear_deadline_checked;
bool mission_body_clear_deadline_feasible;

ShiftOut ownerは、

checked && feasible

を要求します。

選択時はdeadline成立でも、実行中にadaptive closingや曲率速度制限が入れば予測が変わります。残りslackを毎周期更新し、

slack十分:
  mission継続

slack減少:
  closing speed調整

  FollowPrepareではなくmission abort

上位車のLAT-TTCに相当する機能を丸ごと入れなくても、まずこのdeadline-slack monitorだけでかなり改善できます。
